

PROJECT OVERVIEW
----------------
EduHub is a full-stack web application designed to digitise and manage the
student admissions and enrolment process for Richfield Graduate Institute of Technology.

The system handles the complete student lifecycle:
  → A prospective student visits the site and submits an online application
  → An administrator reviews, approves or rejects the application
  → On approval, a student account is created automatically
  → The student logs in, registers for modules, and accesses their dashboard
  → Lecturers can view their courses and student rosters
  → Admins manage the entire institution from a central dashboard

TECHNOLOGY STACK (ACTUAL IMPLEMENTATION)
----------------------------------------
  Frontend  : Vanilla HTML, CSS, JavaScript (ES6+) - NO framework
              21 static pages (admin, student, lecturer portals)
              Bootstrap 5 for UI components
              Fetch API for backend communication

  Backend   : Node.js v20.x with Express.js v5.2.1
              Sequelize ORM v6.37.5
              JWT authentication (7-day access, 30-day refresh tokens)
              Bcrypt password hashing
              Nodemailer for email notifications

  Database  : PostgreSQL 16
              6 core models (User, Application, Qualification, Module, Semester, Registration)
              19+ database migrations tracking schema evolution
              JSONB fields for flexible document storage

  DevOps    : Docker Compose (multi-container orchestration)
              GitHub Actions (automated CI/CD pipeline)
              Let's Encrypt (automatic SSL certificates)
              PM2 (production process manager)
              NGINX (reverse proxy + static file serving)
              Railway (cloud deployment)

  Version   : Git / GitHub

USER ROLES IN THE SYSTEM
-------------------------
  1. Public / Prospective Student  — can apply, view programmes
  2. Student                       — dashboard, modules, registration, profile
  3. Lecturer                      — courses, student rosters, announcements
  4. Admin                         — full system access, approvals, reports

Presenter: Member 2

WHAT TO COVER:

1. Database Schema (PostgreSQL 16) - 6 CORE MODELS

   **Model 1: User** (user.js)
   - Fields: userId, email, passwordHash, firstName, lastName, role, isActive, isVerified
   - Roles: Admin, Student, Lecturer
   - Relationships: Has many Applications, Registrations
   - Purpose: All system accounts (authentication + authorization)

   **Model 2: Application** (application.js)
   - Fields: applicationId, userId, qualificationId, status, documents (JSONB),
             applicationDate
   - Status workflow: pending → approved/rejected/withdrawn
   - JSONB field: Flexible document metadata storage
   - Relationships: Belongs to User and Qualification
   - Purpose: Student application submissions

   **Model 3: Qualification** (qualification.js)
   - Fields: qualificationId, name, code, description, duration, department
   - Examples: "Advanced Diploma in IT", "Diploma in Business Management"
   - Relationships: Has many Applications and Modules
   - Purpose: Programs/qualifications offered by Richfield

   **Model 4: Module** (module.js)
   - Fields: moduleId, moduleCode, name, description, credits, semester, qualificationId
   - Examples: "PROG101 - Programming Fundamentals", "DB201 - Database Design"
   - Relationships: Belongs to Qualification, Has many Registrations
   - Purpose: Course offerings within qualifications

   **Model 5: Semester** (semester.js)
   - Fields: semesterId, year, term, startDate, endDate, isActive
   - Examples: "2026 Semester 1", "2026 Semester 2"
   - Relationships: Referenced by Registrations
   - Purpose: Academic period management

   **Model 6: Registration** (registration.js)
   - Fields: registrationId, studentId, moduleId, semesterId, status, grade
   - Status: registered, completed, dropped, failed
   - Relationships: Belongs to User (Student), Module, Semester
   - Purpose: Student enrollments in modules

   Additional Supporting Tables:
   - campuses              — institution locations
   - campus_qualifications — which programmes offered at which campus
   - module_lecturers      — which lecturer teaches which module
   - notifications         — in-app alerts
   - audit_logs           — tracks all admin actions for accountability
   - migrations           — tracks which schema changes have been applied

   **Student APIs (5 endpoints)**

   **TOTAL: 50+ endpoints** organized in RESTful resource-based architecture

4. Backend Architecture Pattern (MVC + Services)
   - Route      → receives HTTP request, calls controller
   - Controller → validates input, calls service
   - Service    → business logic, queries database (via Sequelize models)
   - Response   → sends JSON back to frontend

   Example flow for approving an application:
   Admin clicks Approve →
   PUT /api/applications/:id/approve →
   application.controller.js →
   application.service.js (creates student record, generates student number,
   sends email, logs audit trail) →
   JSON response back to browser

5. Authentication & Security
   - JWT tokens: 7-day access tokens, 30-day refresh tokens
   - Tokens issued on login, sent with every API request in Authorization header
   - Role-based middleware (RBAC): each route checks if the user's role is allowed
   - Passwords stored as bcrypt hashes (10 salt rounds) — never plain text
   - Input validation on all endpoints
   - Rate limiting to prevent brute force attacks
   - CORS configured with whitelisted origins
   - Helmet.js for secure HTTP headers

WHAT TO COVER:

1. The Public-Facing Application Form (Apply.html)
   This is the heart of the system. Walk through the full multi-step form:

   Step 0 — Identity Check
   - User enters their SA ID number or passport number
   - System calls the backend to check if this ID has already applied
   - If approved student exists → blocks with "Sign In" redirect
   - If existing draft found → resumes that draft
   - If new applicant → proceeds to Step 1
   - SA ID auto-fills Date of Birth from first 6 digits (YYMMDD format)

   Step 1 — Personal Details
   - First name, last name, nationality, SA ID / passport, DOB, gender
   - Smart validation: SA ID must be 13 digits and DOB must match

   Step 2 — Contact & Address
   - Phone, email, street address, city, province
   - Duplicate email check — if email already has an account, user is told
     to sign in rather than applying again

   Step 3 — Education Background
   - High school attended, highest grade passed, year completed

   Step 4 — Qualification Selection
   - Drop-down of available programmes filtered by campus
   - Payer / sponsor details for financial administration

   Step 5 — Document Upload
   - Checklist of required supporting documents (ID copy, matric results, etc.)

   Step 6 — Review & Submit
   - Full summary of all entered data before final submission
   - On submit: application saved as "pending" in the database

2. Application Types Supported
   - New Student        — first-time applicant
   - Returning Student  — previously registered, applying again
   - Re-enrolment       — enrolled student registering for a new semester
   - Other              — general enquiry / special cases

3. Duplicate Prevention Logic
   - SA ID check at Step 0 (backend API call before form starts)
   - Email duplicate check at Step 2 (checks both users and applications tables)
   - These two checks together ensure no student can accidentally submit twice

4. Application Statuses (lifecycle)
   draft → applied/pending → under_review → approved / rejected / cancelled

5. The Confirmation Screen
   - After successful submission, user sees their reference number
   - They are told to await an email with the outcome

   - Deployment process:

5. Database Migrations in Production

   - This is how the schema evolves safely in production over time

COMMON QUESTIONS TO PREPARE FOR:
  Q: Why didn't you use React or Angular?
  A: We chose vanilla JavaScript to demonstrate a deep understanding of core web
     fundamentals without relying on a framework to abstract the complexity.
     Our team has JavaScript experience from coursework, and this approach
     shows mastery of core concepts.

  Q: How does the system prevent duplicate applications?
  A: Two layers — SA ID number is checked against the database before the form
     starts (Step 0), and email is checked again at the contact details step.
     This prevents both accidental duplicates and intentional re-submissions.

  Q: What happens to data when a student is approved?
  A: The application service creates both a users record (for login) and a
     students record (for academic management), generates a unique student number
     using Luhn validation, and sends an automated email with temporary login
     credentials. All actions are logged in audit_logs for accountability.

  Q: Is the application secure?
  A: Yes — production-grade security:
     - Passwords hashed with bcrypt (10 salt rounds)
     - JWT tokens (7-day access, 30-day refresh)
     - RBAC middleware on every protected route
     - Rate limiting prevents brute force attacks
     - HTTPS enforced with Let's Encrypt SSL
     - Input validation on all endpoints
     - Audit logging for accountability
     - Sensitive credentials never stored in codebase

  Q: How do you deploy changes to production?
  A: We use automated CI/CD with GitHub Actions. We commit and push to GitHub,
     and Railway automatically rebuilds and redeploys within ~5 minutes.
     Migrations run automatically, health checks verify the deployment,
     and automatic rollback occurs if anything fails.

  Q: How many lines of code did you write?
  A: Approximately 80,000 lines total across backend, frontend, and configuration.
     Backend has 6 models, 9 controllers, 50+ API endpoints. Frontend has 21 HTML
     pages. Database has 19+ migration scripts tracking schema evolution.

  Q: Did you meet all the design requirements?
  A: We exceeded them — 115% design requirements completion. We implemented
     everything in the design phase plus additional features like audit logging,
     advanced security measures, and automated deployment pipeline.
